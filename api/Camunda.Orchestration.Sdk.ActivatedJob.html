Properties

Clock

The clock the worker's own cadence runs on. Handlers should read time and wait through this rather than DateTimeOffset.UtcNow or Task.Delay(ms, ct), so that in-handler timing is virtual whenever the client's clock is.

var startedAt = job.Clock.GetUtcNow();
await Task.Delay(TimeSpan.FromMilliseconds(200), job.Clock, ct);

This is for short in-handler coordination — poll again shortly, back off before a retry, debounce. It is not for business waits: "wait three days, then escalate" belongs in the BPMN model as a timer event, which is durable, owned by the engine, and survives worker restarts.

CustomHeaders

Raw custom headers (typically a JsonElement at runtime).

 <p><b>Untrusted input.</b> Custom headers are defined in the process model, not written by
 process starters, service tasks or forms, so they are controlled by whoever can deploy or
 change the model — a narrower group than the one that controls <xref href="Camunda.Orchestration.Sdk.ActivatedJob.Variables" data-throw-if-not-resolved="false"></xref>, but
 still not your handler's own code. See <xref href="Camunda.Orchestration.Sdk.ActivatedJob.Variables" data-throw-if-not-resolved="false"></xref> for the rest of the trust
 model.</p>

Variables

Raw variables (typically a JsonElement at runtime).

 <p><b>Untrusted input.</b> The content is whatever was written into the process
 instance — by whoever started it, by an earlier service task, or by a form submission — so
 treat it as you would an HTTP request body, not as configuration.</p>

 <p>What the SDK guarantees: deserialization happens only when you ask for a type, and
 only into the type you name (<xref href="Camunda.Orchestration.Sdk.ActivatedJob.GetVariables%60%601(System.Text.Json.JsonSerializerOptions)" data-throw-if-not-resolved="false"></xref>). There is no unrestricted
 type-name resolution — the payload cannot name a type for the SDK to load — though
 <code>System.Text.Json</code> will dispatch to polymorphic subtypes that your own target type
 declares. Depth is bounded by the <code>System.Text.Json</code> default <code>MaxDepth</code> of 64,
 applied to the activation response as a whole (the envelope around the job takes the first
 levels of that budget), so a deeply nested payload fails with a <code>JsonException</code> during
 activation rather than recursing without bound. The SDK does not log variable payloads —
 with indirect routes: an exception that escapes the handler, other than the SDK's own
 <code>JobFailureException</code> and <code>BpmnErrorException</code>, is logged with its message and
 stack and its message is sent to the broker as the job's failure message. That includes a
 <code>JsonException</code> thrown by <xref href="Camunda.Orchestration.Sdk.ActivatedJob.GetVariables%60%601(System.Text.Json.JsonSerializerOptions)" data-throw-if-not-resolved="false"></xref>, which you call from the
 handler and whose message and path can name payload properties. The two control exceptions
 are not logged, but their messages are still sent to the broker (as the failure message or
 the BPMN error message), and a handler cancelled by worker shutdown is not reported to the
 broker (only a debug line naming the job key is logged). A failure while the activation
 response itself is parsed happens before a handler exists: the poll loop logs it, but there
 is no job to fail, so nothing is sent to the broker. A single job that cannot be converted
 afterwards is logged at warning level with its exception and skipped, also without a
 report to the broker. The exception to the poll-loop log is a parse failure on a requested
 lease token: it is replaced by a <xref href="Camunda.Orchestration.Sdk.LeaseNotHonoredException" data-throw-if-not-resolved="false"></xref> (naming a
 placeholder job key and the <code>withLease</code> flag, not payload content; the original parse
 exception is not kept) that faults the poll task, so it reaches the caller through
 <xref href="Camunda.Orchestration.Sdk.JobWorker.Completion" data-throw-if-not-resolved="false"></xref> instead. Nothing redacts exception contents.</p>

 <p>What the SDK does not do: there is no size cap on a payload, no schema validation,
 and no sanitisation. Conversion to a target type is <code>System.Text.Json</code> behaviour: by
 default, for an ordinary DTO, properties that do not match are ignored and missing ones keep
 their initializer or default, while <code>required</code> or <code>[JsonRequired]</code> members make
 an absent property throw and custom options can reject unmatched properties. Validate what
 you depend on, and escape anything you pass onward to a shell, a query, a path or a
 page.</p>

Methods

GetCustomHeaders<T>(JsonSerializerOptions?)

Deserialize the job's customHeaders payload into a strongly-typed DTO.

The payload is untrusted input — see CustomHeaders.

GetVariables<T>(JsonSerializerOptions?)

Deserialize the job's variables payload into a strongly-typed DTO.

The payload is untrusted input — see Variables. Deserializing into T is a shape conversion, not validation: with the default options, unmatched properties are ignored and absent ones keep their initializer or default, unless T marks them required or you pass options that reject unmatched members. A payload that does not fit throws a JsonException whose message can name payload properties; see Variables for where exception messages end up. options can only tighten the depth bound on this element: it was parsed off the activation response under the System.Text.Json default MaxDepth of 64 already, so a larger value here cannot admit a payload that activation rejected.
